## 0. 结论先行（TL;DR）

1. **路线判断成立**：三菱 GX Works3 的四种语言里，只有 **ST 是"文本原生"** 的——可被 AI 生成、diff、静态分析、自动导入、自动测试；梯形图/FBD 的剪贴板是专有二进制，SFC 结构复杂。把 AI 编程押在 ST 上，是当前约束下的最优解。

2. **落地路线已经找到"官方通道"（本方案最重要的新事实）**：GX Works3 官方支持 **IEC 61131-10 XML 导入**，
   一次可导入「程序块 + ST 程序本体 + 局部标签 + 全局标签 + 结构体 + FB/函数」；本机就有官方样例
   `SampleData\IEC61131-10XML\Sample.xml`、手册附录（附8）与内嵌 XSD。v0.1 当年"XML 导入后程序为空"
   的真正原因是：它生成的是 **PLCopen TC6_0201** 格式（`<project>` 小写、`plcopen.org` 命名空间），
   而 GX Works3 要的是 `<Project>` + `www.iec.ch/public/TC65SC65BWG7TF10` —— **是格式用错，不是三菱缺陷**。
   因此全自动主线 = **模板工程 + IEC 61131-10 XML 导入 + RebuildProject + 证据导出**。
   （详见 `01-GXWorks3原生接口.md` §7；`M9` 实验可最终确认根因。）

3. **但 v0.1 只是"代码生成器"，不是"AI 编程系统"**。它解决了"生成像样的三菱 ST + 标签 CSV"，
   没解决三件事：**真实编译器闭环、行为验证、零人工落地**。AI 写 PLC 代码的风险 90% 不在"写不出来"，
   而在"本地检查通过、GX Works3 编译不过、上机行为不对"。

4. **本方案的核心是把"GX Works3 编译器 + 仿真器"接进 AI 的反馈回路**：
   `需求规格 → 程序中间表示(IR) → IEC61131-10 XML / ST + 标签 → GX Works3 原生导入/编译 → 编译诊断回灌修复 → GX Simulator3 场景测试 → 交付工程包`。
   本项目已确认的关键基础设施（见 §3）让这条闭环第一次具备工程可行性。

5. **编译通过 ≠ 行为正确**（2026 年 LLM-PLC 评测论文的核心结论）：验收口径必须是
   `L0 本地检查 + L1 原生编译通过 + L2 安全规则 P0=0 + L3 仿真场景通过`；
   "一次通过率（FTR）"比"编译通过率（CPR）"更能反映真实价值（详见 `03-验证体系与行业实践.md`）。
   程序按 🔴红/🟡黄/🟢绿 分级，**红色（急停/安全门/安全 PLC）禁止 AI 生成**。

6. **建议按 4 个里程碑推进**（§12）：M0 打通原生闭环（1~2 周）、M1 生成管线工程化（2~3 周）、
   M2 仿真验证闭环（2~3 周）、M3 产品化/MCP（2~3 周）。**M0 是所有后续工作的前提**，先做。

7. **三个必须先修的事实性问题**（否则 AI 生成得再漂亮也编译不过）：
   - v0.1 的软元件范围是 **FX3U 口径**，不是 FX5U（X/Y 应为 X0~X1777 八进制、M0~M32767 等，见 §4.2）；
   - ST 字符串常数在 GX Works3 中必须用**单引号**（双引号是 WSTRING）；
   - 指令/FB 白名单需要按 CPU 系列（iQ-F vs iQ-R）数据驱动，不能混用。

## 1. 目标与边界

### 1.1 产品定位

一个 **AI 辅助的 GX Works3 ST 工程工作台**：工程师用自然语言/IO 表/工艺描述提出需求，
工具产出**可直接导入 GX Works3、能原生编译通过、并通过仿真场景验证**的 ST 工程，
同时输出可审查、可追溯的交付物。

目标用户：

- 三菱 PLC 集成商/设备厂的程序员（FX5U、iQ-R 为主）：把"写初稿 + 对标签 + 编译排错"从数小时压到分钟级；
- 想用 AI 提效但被"AI 不懂三菱方言""生成的东西不敢上机"卡住的团队；
- 上层 Agent（Claude/DeepSeek/自研）通过 MCP 调用本工具链做自动化编程。

### 1.2 成功标准（可度量）

| 指标 | 目标（M3 结束时） |
|---|---|
| 基准场景**一次通过率（FTR，首轮无修复）** | ≥ 60%（18 个基准场景） |
| 原生编译通过率（CPR，含修复循环） | ≥ 95% |
| 仿真行为用例通过率（BPR） | ≥ 85%，safety 类 100% |
| 端到端耗时（需求→可编译工程） | ≤ 10 分钟/中等程序 |
| 人工返工（MRO） | 中位数 ≤ 20 分钟/程序 |
| 方言类错误（跨品牌指令/类型/地址） | 0 容忍（静态检查 + 编译器双拦截） |

### 1.3 非目标（本期不做）

- **不做安全功能**：安全 PLC、SIL/PL 回路、急停硬线回路不进入 AI 生成范围（见 §10.5）；
- **不做梯形图/FBD 生成**：图形语言的语义与落地成本高（剪贴板专有二进制；虽有指令表 CSV 导入但不承载图形语义），投入产出比低；
- **不做硬件配置**：CPU/模块/网络参数由 GX Works3 工程模板提供，不由 AI 生成；
- **不做 PLC 下载写程序**：只读在线（仿真/实机监视、设备读写、测试）可以，写 PLC 程序必须人工确认；
- **不承诺零人工**：保留"人工审查 + 关键节点确认"的治理 gate。

## 2. 为什么是 ST（技术路线论证）

### 2.1 四种语言的"可 AI 化"对比

| 语言 | AI 生成难度 | 落地方式 | 可测试性 | 结论 |
|---|---|---|---|---|
| ST（结构化文本） | 低（文本、类 Pascal） | **文本粘贴/导入** | 高（可解析、可 diff、可单测） | **主路线** |
| 梯形图 LD | 高（图形语义、双线圈/扫描顺序） | 剪贴板专有二进制；另有指令表 CSV 导入，但不承载图形语义 | 低 | 不做 |
| FBD/LD | 中高 | 同上 | 低 | 不做 |
| SFC | 中 | 结构复杂、落地难 | 中 | 暂不做 |

### 2.2 GX Works3 的硬约束（决定架构）

| 元素 | 存储位置 | 外部可写方式 | 结论 |
|---|---|---|---|
| 工程文件 `.gx3`/`.gxp` | 专有二进制 | ❌ 直接读写不可行 | 通过官方 Open Interface 或 UI 自动化操作 |
| 全局标签 | 全局标签表 | ✅ CSV 导入 / OpenIF | 可自动 |
| 局部标签 | 各 POU 的「局部标签编辑器」独立维护 | ✅ CSV 导入 / IEC XML 随工程导入 | 可自动 |
| ST 程序本体 | POU 的「程序本体」工作表（纯文本） | ✅ 粘贴 / IEC 61131-10 XML 导入（官方格式已核实） | 可自动 |
| 梯形图本体 | 梯形图编辑器 | ❌ 剪贴板专有二进制 | 不做 |
| IEC 61131-10 XML 整体导入 | 工程菜单 / OpenIF `ImportProjectXml` | ✅ **官方支持**：一次导入程序块 + ST 正文 + 局部/全局标签 + 结构体 + FB；本机有官方样例与 XSD | **主路径（A）**，用官方 `Sample.xml` 校准 |
| 梯形图指令列表 CSV | 编辑菜单导入 | ✅ 支持指令列表 CSV 导入（8 列后忽略） | 不做（不生成 LD），仅作背景认知 |

> 结论：**变量声明与程序本体分离**是 GX Works3 的结构性约束，所以任何 AI 方案都必须同时产出
> "ST 文本 + 标签定义 + 落地动作"三件套。v0.1 已经把三件套的文件格式摸清（标签 CSV 的 TAB/UTF-16LE/27-28 列等），
> 这是本项目最有价值的既有资产之一。

### 2.3 AI 的能力错配（真正的风险来源）

LLM 的三菱知识是"二手"的：它默认按 IEC 61131-3 / 西门子 / CODESYS 习惯写代码。典型翻车：

- 用西门子/CODESYS 函数（`IREF`、`POKE`、`SCALE`、`ROL`）；
- 整数/浮点隐式转换（三菱不允许，必须 `REAL_TO_INT`）；
- 标准 FB 形参名写错（`RS` 的 `S/R1/Q1`、`SR` 的 `S1/R/Q1`）；
- 设备地址口径错（FX3U vs FX5U、X/Y 八进制）；
- 字符串引号、注释语法、`SET/RST` 函数语义等方言细节。

**因此本方案的核心不是"更好的提示词"，而是三件事的组合**：
① 可验证的方言知识库（数据驱动、可测试）；② 真实编译器作为唯一真相源；③ 结构化修复循环。

### 4.2 已确认的事实性错误（必须先修）

| 项 | v0.1 写法 | 官方手册事实 | 影响 |
|---|---|---|---|
| FX5U 软元件范围 | X/Y 0–511、M 0–767、S 0–127、T 0–511、C 0–255、L 0–767 | **X0~X1777、Y0~Y1777（八进制）、M0~M32767、L0~L32767、S0~S4095、T0~T1023、ST0~ST1023、C0~C1023、D0~D7999、R0~R32767**（FX5S/5U/5UC；FX5UJ 更小） | 合法地址被误报、越界地址被放过；AI 被误导 |
| X/Y 地址进制 | 按十进制解析 `(\d+)` | X/Y 是**八进制**（X1777 = 1023） | `X1777` 被当成 1777 判越界 |
| ST 字符串常数 | 未约束（AI 常用双引号） | ST 中 STRING 用**单引号**，双引号是 WSTRING | 编译错误/类型不符 |
| 指令/FB 名 | `OUT_M/OUT_H/OUT_L/TIMER_T/COUNTER_FB/RAMP` 等 | 6 本手册全文检索**不存在**；正确名为 `COUNTER_FB_M`、`TIMER_*_FB_M`、`RAMPF`（指令）等，且 iQ-F/iQ-R 分系列 | 生成不可编译代码 |
| 类型表 | 含 `LINT`、`ULINT`、`LREAL` | FX5 不支持这些类型（支持 BOOL/WORD/DWORD/INT/DINT/REAL/TIME/STRING/WSTRING/TIMER/COUNTER 等） | 本地放行、GX 编译失败 |
| FB 调用语法 | 代码/提示词统一用 `=>`，成员访问 `.Q` | 手册示例用 `:=`（`Q:=d1`）；`=>` 与 `.Q` 需原生编译验证 | 可能全部 FB 调用写法错误 |
| REPEAT/块注释/SQRT | REPEAT 反解析缺 `END_REPEAT`；生成 `(* *)` 块注释；白名单含 SQRT | ST 中 SQRT/LIMIT 指令不支持（用通用功能）；REPEAT/块注释语法待原生验证 | 语法/编译风险 |
| 分析器 target | `--target iQ-R` 只存不用，设备/FB 规则固定 FX5U | iQ-R 的 X/Y 为**十六进制**、上限 X0~X2FFF（小机型 X1FFF） | 双 CPU 支持名不副实 |
| 错误恢复 | `recovery.ts` 行号偏移、丢弃已解析语句、存在死循环风险 | 实测 `bad_example.st` 的 E015/E009 漏报、行号 −5 | 本地诊断不可信 |
| 标签注释 | lexer 丢弃 `//`，CSV 注释列恒为空 | GX Works3 标签 CSV 有注释列 | 交付物无变量说明，可维护性差 |
| 地址分配假设 | `AUTO_ALLOCATE_GUARD`（M8000/D512）无手册依据；地址冲突检查空实现 | 手册：未分配软元件进入标签存储器，不等于"自动分配地址" | 可能生成错误地址策略 |
| 早期 XML 方案 | `build-xml` 生成 **PLCopen TC6_0201**（`<project>`、`plcopen.org` 命名空间） | GX Works3 需要 **IEC 61131-10**（`<Project>` + `www.iec.ch/public/TC65SC65BWG7TF10`） | 早期"XML 导入后程序为空"的结论错误；XML 应升级为主路径 |
| 文档一致性 | 导入指南说标签可用 XML、有 build-xml | 实际 XML 只能导出、代码无 build-xml | 误导操作 |

> 这些错误说明：**方言知识必须数据驱动、带出处、可回归测试**，而不是散落在 TS 常量里。
> 这是 §7.2 知识库模块存在的理由。

## 5. 总体架构

### 5.1 分层架构

```
┌─────────────────────────────────────────────────────────────────────┐
│  交互层   CLI（人/CI）        MCP Server（Agent）      可选 Web 审查 UI │
├─────────────────────────────────────────────────────────────────────┤
│  规格层   natural language / IO 表 / 工艺描述 → Spec JSON（人工确认）    │
├─────────────────────────────────────────────────────────────────────┤
│  知识层   CPU 档案 │ 指令/FB 库 │ 代码模板库 │ 手册 RAG │ 项目上下文提取    │
├─────────────────────────────────────────────────────────────────────┤
│  生成层   模板组装 + LLM 生成（声明 + ST 正文）→ 解析为 Program IR        │
├─────────────────────────────────────────────────────────────────────┤
│  分析层   解析/类型/符号/控制流/安全规则 → 结构化诊断（带修复建议）        │
├─────────────────────────────────────────────────────────────────────┤
│  原生层   GX Works3 适配器：建/开工程、导标签、写程序、编译、诊断采集       │
├─────────────────────────────────────────────────────────────────────┤
│  执行层   GX Simulator3 场景测试（驱动输入/断言输出/时序）               │
├─────────────────────────────────────────────────────────────────────┤
│  证据层   编译报告/场景报告/覆盖与规则命中/成本 → 评测基准与回归          │
├─────────────────────────────────────────────────────────────────────┤
│  交付层   工程包（.gx3 + ST + 标签 + 报告）与追溯矩阵                   │
└─────────────────────────────────────────────────────────────────────┘
```

### 5.2 主数据流（一次生成的真实闭环）

```
用户需求
  │ 1. 结构化（LLM + 模板）
  ▼
Spec.json ────────────── 人工确认 gate ①
  │ 2. 选模板/组组件 + LLM 生成
  ▼
Program IR（POU/变量/语句树/标签/设备映射）
  │ 3. 确定性发射
  ▼
ST 源码 + 标签定义 + 工程清单
  │ 4. 本地分析（L0/L2 规则）
  ▼
GX Works3 工程（模板复制或新建）
  │ 5. OpenIF：导入标签/程序 → BuildProjectExt
  ▼
编译结果 ──失败──► 诊断解析 → 修复建议 → 回灌 LLM/模板（最多 N 轮）
  │ 通过
  ▼
GX Simulator3（L3）：按测试用例驱动 X/D，断言 Y/M/D
  │ 失败 → 回到生成/修复
  ▼
交付包（工程/源码/标签/编译报告/测试报告/追溯矩阵）── 人工审查 gate ②
```

### 5.3 核心设计原则

1. **编译器是唯一真相源**：本地检查只做"提前拦截"，绝不宣称"能编译"。
2. **LLM 不做最终输出者**：它产出声明 + ST 正文，必须经过解析器 → IR → 规则 → 编译器四级关卡。
3. **知识可验证**：每条方言规则/指令签名都带出处（手册编号/页码/URL）与回归测试。
4. **模板优先**：80% 的工业逻辑是标准回路，用经过验证的模板生成，AI 只填参数/组合；自由生成兜底。
5. **可复现**：固定 spec 输入、固定模型参数/seed、记录版本与工具链哈希，任何结果可重跑。
6. **证据链完整**：需求↔代码↔测试↔报告可追溯；没有验证报告的代码不得交付。
7. **安全边界硬编码**：安全相关关键字/回路进入"禁止 AI 生成"清单，只允许人工实现 + 工具检查。
8. **渐进式**：每个里程碑都能独立交付价值，不追求一次性大重构。

## 6. 关键设计决策（ADR 摘要）

| # | 决策 | 理由 | 备选与否决原因 |
|---|---|---|---|
| D1 | 主路线 = ST，不碰 LD/FBD/SFC 生成 | 文本可验证、可落地；其余语言落地成本高 | LD 剪贴板专有二进制 |
| D2 | 生成产物 = `Program IR`，ST 文本只是发射结果 | 可校验/可测试/可多目标发射；IR 让"AI 输出"与"工程落地"解耦 | 直接让 LLM 自由写 ST：不可控、难修复 |
| D3 | LLM 输出"声明 + ST 正文"，由解析器转 IR（v0.1 的 JSON 结构可复用） | 保留 LLM 表达力，又强制过语法关；迁移成本最低 | 让 LLM 输出完整 AST：约束太强、模型易错、提示词复杂 |
| D4 | 双模生成：**模板库优先，LLM 兜底** | 标准回路用模板=确定、可测；LLM 处理非标逻辑 | 纯 LLM：错误率高、成本高；纯模板：覆盖不足 |
| D5 | 原生验证走 GX Works3 OpenIF（GXW3Call），UI 自动化仅兜底 | 官方接口稳定、可拿编译结果；UI 自动化脆弱 | 只靠 UI：版本/DPI/焦点问题多；只靠本地检查：不可信 |
| D6 | 工程落地用 **工程模板 + 导入**，而不是从零生成硬件配置 | 模块配置/参数无法由 AI 可靠生成；模板保证可编译基线 | 从零 CreateNewProject：需处理 CPU/模块/任务配置 |
| D7 | 标签策略：局部标签自动分配（软元件留空），全局标签显式地址 | 局部自动分配避免地址冲突；HMI/通信必须显式地址 | 全部显式：易冲突；全部自动：HMI 无法寻址 |
| D8 | 验证金字塔 L0~L4，编译与仿真为必过 gate | 只做静态检查无法证明行为 | 只做单测/仿真：不能替代真实编译 |
| D9 | 知识库数据驱动（JSON + 出处 + 测试），不写死在代码 | 三菱型号/固件差异大；便于升级与评审 | 硬编码：已证明会错（FX3U 口径） |
| D10 | 同时提供 CLI 与 MCP Server | 人用 CLI/CI；Agent 用 MCP；一套核心 | 只做 CLI：Agent 集成难；只做 Web：自动化难 |
| D11 | 每次生成固定快照与报告，禁止"静默覆盖"现有工程 | 工业现场必须可回退、可审计 | 直接改用户工程：风险不可接受 |
| D12 | 不生成安全功能代码；安全相关只做检查与提示 | 责任边界与法规要求 | — |

## 7. 模块设计

### 7.1 规格层（Spec）

**职责**：把自然语言/表格/工艺描述变成可确认、可测试的结构化规格。

Spec 结构（草案）：

```jsonc
{
  "meta": { "project": "水箱控制", "cpu": { "series": "FX5U", "model": "FX5U-32MT/ES" }, "version": "1.0" },
  "io": [ { "device": "X0", "name": "bStart", "type": "BOOL", "comment": "启动按钮" } ],
  "vars": [ { "name": "tRun", "type": "TON", "scope": "local" } ],
  "modes": ["手动", "自动"],
  "states": [ { "id": "IDLE", "next": ["RUN"] } ],
  "requirements": [
    { "id": "R1", "text": "按下启动按钮，水泵 Y0 启动", "verify": "T1" }
  ],
  "alarms": [ { "id": "AL1", "cond": "X2 = TRUE", "action": "停泵 + Y1 报警" } ],
  "safety": { "estop": "X10", "interlocks": ["Y0 与 Y1 不得同时为 ON"] }
}
```

要点：
- **IO 表是一等公民**：AI 不许"臆造"地址；所有 X/Y 必须来自 spec 或既有工程上下文；
- 需求带 ID，后续追溯矩阵与测试用例引用同一 ID；
- spec 经人工确认后**冻结版本**，后续生成与评测都以它为输入（可复现的前提）。

### 7.2 知识层（Knowledge）

**职责**：把"三菱方言正确性"从提示词里的散装描述，升级为可查询、可测试、带出处的数据。

组成：

| 子模块 | 内容 | 来源 | 用途 |
|---|---|---|---|
| `knowledge/cpu/<model>.json` | 软元件范围（含八进制/锁存区）、语言支持、扫描周期、任务类型 | 手册（iQ-F/iQ-R） | 校验地址/生成约束 |
| `knowledge/instructions/<family>.json` | 指令/函数/FB 的 ST 形式、EN/ENO、操作数类型、可用设备、限制 | 编程手册（iQ-F/iQ-R） | 生成与诊断 |
| `knowledge/fb/standard.json` | IEC 标准 FB（TON/RS/CTU…）形参表 | IEC 61131-3 + 手册验证 | 校验 FB 调用 |
| `knowledge/patterns/*.md` | 经过验证的代码模板（启停/联锁/定时/计数/状态机/模拟量/PID/报警/手自动） | 团队实践 | 模板生成 |
| `knowledge/manuals/` | e-Manual 抽取的正文 + 页码/URL + 关键词索引 | 本机 e-Manual（SQLite 可直接抽） | RAG + 事实核查 |
| `knowledge/rules/*.json` | 编码规则/安全规则（双线圈、输出互斥、急停、扫描时间等） | 行业规范 + 手册 | L2 检查 |

工程要求：
- 每条数据带 `source`（手册号/章节/URL）、`verified_at`、`test`（正/反例）；
- 用测试锁死：`knowledge/*.json` 的每个声明至少对应一个"应通过/应报错"的 ST 片段；
- 升级 CPU/固件版本时，只改数据 + 跑回归，不改代码逻辑。

> 已有实证：本机 e-Manual 的 `.ema` 解包后是 SQLite（`TBL_CONTENT` 表存 HTML 正文），
> 可批量导出"软元件一览/指令表/ST 语法"等章节，构建带出处的高质量语料。这是本项目相对开源方案的低成本优势。

### 7.3 生成层（Generate）

**职责**：把 Spec 变成 IR/ST，并保证"一次成功率"。

三个子流程：

1. **模板组装（主力）**：从 `patterns/` 选择模板（如"电机启停 + 故障联锁 + 10s 自动停"），
   用 Spec 参数实例化，模板本身是经过编译与仿真验证的代码 → 确定性输出。
2. **LLM 生成（非标逻辑）**：上下文注入 = Spec + CPU 档案 + 可用指令子集 + 相关模板 few-shot + 静态检查规则；
   输出"声明 + ST 正文"JSON；模型可多轮修复。
3. **修复循环（关键）**：把三层诊断按顺序回灌给模型：
   - L0 解析错误（带行号/期望 token）；
   - L2 规则/类型错误（带规则 ID 与修复建议）；
   - L1 GX Works3 编译错误（最关键，真实错误码/描述）。
   仅回灌"可修复"的诊断；同一错误连续 2 轮不解决则降级到人工/模板重选，避免死循环。

提示词工程要点：
- **指令白名单按 CPU 系列动态生成**（不是固定一段）；
- few-shot 用"编译通过 + 仿真通过"的黄金样例（从模板库取）；
- 明确输出 schema + "禁止跨品牌写法" + "字符串单引号"等硬规则；
- 让模型输出"意图→状态机→代码"的中间步骤（可审查、可定位）。

### 7.4 分析层（Analyze）

在 v0.1 基础上扩展为四类检查：

| 层 | 检查 | 例子 |
|---|---|---|
| 语法 | 解析、语句恢复 | 缺分号、保留字、块结构错 |
| 语义/类型 | 符号表、类型兼容、隐式转换、FB 形参、设备地址 | `REAL := INT`、`RS(SET:=…)`、`X1777` 越界 |
| 控制流/数据流 | 未初始化使用、双线圈/多驱动、不可达分支、FB 实例复用、除零、定时器单位 | 同一 `Y0` 在两条分支被驱动；`TON.PT` 用 `T#10s` 之外写法 |
| 安全/结构规则 | 输出互锁、急停优先、扫描周期预算、报警复位、模式切换互锁 | 无 `bStop` 路径的启停回路 |

诊断输出 JSON：`{ rule, severity, file, line, col, pou, message, hint, fixable, source }`。

### 7.5 原生层（Native / GX Works3 Adapter）

**职责**：把"生成结果"变成"GX Works3 里真实存在、可编译的工程"，并把编译结果拿回来。

三个通道，统一抽象接口 `GxWorks3Adapter`：

```
interface GxWorks3Adapter {
  createProjectFromTemplate(template, targetPath, cpu): Promise<ProjectRef>
  importProjectXml(project, xmlPath): Promise<ImportResult>   // 路线 A 主通道（IEC 61131-10）
  importObjectCsv(project, csvPath, objectName, objectType): Promise<ImportResult> // 备选
  importLabels(project, labelFiles): Promise<void>            // 路线 B/C 用
  importProgram(project, pouName, stText): Promise<void>      // 路线 B 用（UI 粘贴实现）
  rebuild(project, checkProgram?): Promise<BuildResult>       // 三计数 + 诊断（可读部分）
  exportEvidence(project, outDir): Promise<void>              // 已用设备/标签、HTML、XML 快照
  save(project): Promise<void>
  close(project): Promise<void>
  startSimulator(project): Promise<SimSession>
  readDevices(session, addrs): Promise<Values>
  writeDevices(session, values): Promise<void>
}
```

- **通道 A（首选）**：GXW3Call OpenIF（COM）。已确认存在：`CreateNewProject`、`Export/ImportProjectXml`、
  `ExportObjectCsv/ImportObjectCsv`、`BuildProjectExt/RebuildProjectExt`、`GetPOUNames`、`GetLabels`、
  `ExportUsedDeviceAndLabel`、`ExportProgramViewHtml`、`StartSimulator/StopSimulator`、`OpenOnline/DeviceRead*/DeviceWrite*`。
  IEC 61131-10 XML 格式已核实（官方样例 + XSD），剩余未知项：`ImportProjectXml` 的 flags/mode、
  `ExportProjectXml` 的 bFormat、编译错误明细获取方式（详见 §9.3）。
- **通道 B（兜底）**：UI 自动化（应用已具备 PowerShell + UIAutomation 的桥）：打开工程 → 右键导入标签 CSV →
  打开 POU -> Ctrl+A/Ctrl+V 粘贴 ST → 菜单"转换" → 从输出窗口抓错误文本。
  脆弱点：焦点/DPI/版本差异，需做成"可降级、可人工接管"。
- **通道 C（保底）**：v0.1 的人工导入流程（生成文件 + 操作清单），永远保留。

### 7.6 仿真层（Simulate & Test）

**职责**：无硬件验证行为，产出一份"场景测试报告"。

- 会话管理：`StartSimulator` → 写入工程 → `OpenOnline`（仿真模式）→ 设备读写 → 停止；
- 测试 DSL（草案，详见 `03-验证体系与行业实践.md`）：

```yaml
# test/motor_stop_10s.yaml
name: 电机启停 + 10s 自动停
target: { project: demo, cpu: FX5U }
given:
  X0: false       # 启动按钮
  X1: false       # 停止按钮
when:
  - set: { X0: true }
  - wait: 1
  - set: { X0: false }
then:
  - expect: { Y0: true }
  - wait: 10.5
  - expect: { Y0: false }
assertions:
  - never: { Y0: true, X2: true }   # 故障时不得输出
  - settle_ms: 50
```

- 时序语义要写进 DSL（"wait 以扫描周期为单位，轮询设备值"），否则测试不可复现；
- 覆盖：正常流程、边界（值为 0/最大值）、故障注入（急停、传感器抖动、断电保持）、模式切换。

## 9. 落地通道技术方案（本项目最大的不确定性）

### 9.1 目标

`ai-st native build` 一条命令做到：在临时目录复制工程模板 → 导入 IEC 61131-10 XML（程序体 + 标签一次到位）
→ Rebuild → 返回结构化结果并导出证据 → 保存工程；全程不弹人工对话框（或可接受的最小 UI 自动化）。

### 9.2 已确认的 OpenIF 能力（来自 GXW3Call 类型库，实测 dump）

| 能力 | 方法（节选） | 确定度 |
|---|---|---|
| 建工程/打开/保存/关闭工程 | `CreateNewProject`、`OpenProject`、`AttachProject`、`SaveProject`、`SaveAsProject` | 高（签名明确） |
| 工程 XML 导出/导入 | `ExportProjectXml`、`ImportProjectXml`（含 flags/mode） | **高**：格式已核实（IEC 61131-10 官方样例/XSD）；剩余未知是 flags/mode 取值 |
| **程序体写入（XML 通道）** | `ImportProjectXml`：ST 正文在 `Program/MainBody/BodyContent xsi:type="ST"`，标签在同文件 `Vars`/`GlobalVars` | **高**（格式已核实）→ 路线 A 的核心 |
| 对象 CSV 导出/导入 | `ExportObjectCsv`、`ImportObjectCsv`（objectType/languageType/conversionMethod） | 中（ST 是否支持待验证，作备选） |
| 编译 | `BuildProject`、`BuildProjectExt`、`RebuildProject`（含 bCheckProgram） | 高 |
| 查询 | `GetPOUNames`、`GetGlobalLabelListNames`、`GetLabels`、`GetLabelAssignment`、`GetProgramNo` | 高 |
| 导出报告 | `ExportUsedDeviceAndLabel`、`ExportProgramViewHtml`、`ExportParameterXml` | 高 |
| 仿真 | `StartSimulator`、`StopSimulator`（View）、`GetSimulatorNo` | 高 |
| 在线读写 | `OpenOnline`、`IsPlcOnline`、`ReadDeviceRandom`、`DeviceRead*/DeviceWrite*`、`ExecuteSLMPCommand` | 高 |
| 工程对比 | `SimpleVerifyProject`、`SimpleVerifyProjectDiff` | 高 |
| 错误码可读化 | `GetErrorMessage`（Communication 接口） | 高（仅"错误码→文本"，缺行号/网络定位） |
| **程序体直接写入** | 类型库中**没有** `SetPOUBody/SetProgramSource` 类方法 | 需通过导入/剪贴板 |

### 9.3 M0 验证实验（按优先级，摘自 `01-GXWorks3原生接口.md` §6）

> 前置：**COM 调用环境已由 Lead 验证可行**——32 位 PowerShell 晚绑定（无需 `GXW3Call.Interop.dll`）
> 可创建 Product/Session 对象并 `Initialize(transmitter)`；`GetOpenIFVersion()` 返回 34。
> 方法级调用（建工程/编译）仍需下列实验确认。

| ID | 目的 | 输入 / 操作 | 判定 / 回退 |
|---|---|---|---|
| **M0** | **反推"可导入 XML"格式（最高优先）** | 人工建最小 ST 工程 → `ExportProjectXml` 以 bFormat=0/1 各导一次 → `ExportObjectXml` 同对象 | 至少一种导出物含 `<Project…>`、`MainBody/BodyContent xsi:type="ST"><ST>…</ST>` 与 `Vars/GlobalVars`；否则扩大 bFormat 扫描 |
| **M1** | 打通 OpenIF 调用环境 | `Initialize→GetOpenIFVersion→GetPlcSeriesList→GetLanguageTypeList` | 返回系列/机型/语言列表（应含 ST）；失败记录 HRESULT、检查 STA/管理员/桌面会话 |
| **M2** | `CreateNewProject` 行为 | FX5U/iQ-R + `dwLanguageType` 枚举试探 → `GetPOUNames` | 明确是否自带 Program/任务/默认标签；若不自带 → 固化"模板工程"策略 |
| **M3** | **IEC 61131-10 导入闭环（路线 A 核心）** | 按官方 `Sample.xml` 改造：1 个 Program（ST 正文）+ 局部/全局标签 | 程序本体出现 ST 源码、标签数量/类型正确；若空 → 按命名空间/FileHeader/BodyContent 逐项排查（对照 `01` 文档 §7） |
| **M4** | ST 对象 CSV 往返（备选通道） | `ExportObjectCsv(program, objectType=?)` → `ImportObjectCsv(languageType=?, conversionMethod=?)` | CSV 含完整 ST 且导入等值 → 多一条细粒度通道；否则关闭 |
| **M5** | 编译与错误证据 | 一好一坏两个工程 → `BuildProject/RebuildProject` → 读三计数 + UI Output 窗口 + `IsProjectCompiled`/`GetFileListForDownload` | 好工程 error=0 且可下载文件非空；坏工程 error>0 且 Output 有错误文本 |
| **M6** | `ImportProjectXml` 合并/替换语义 | 同一工程连续导两次（改标签名） | 明确 flags/mode 的"追加/替换/跳过"组合；用 `SimpleVerifyProject` 做前后对比 |
| M7（可选） | UI 自动化稳定性 | 模板工程 + 10 份 ST，粘贴→转换→读 Output→保存，重复 50 次 | 成功率 ≥95% 才可承诺全自动 UI；否则 A 为唯一主线 |
| M8（可选） | Register Label 路线 | 未声明变量的 ST → 未定义标签登录对话框 | 只能逐条登记 → 仅作补丁场景 |
| M9 | v0.1"XML 导入为空"根因 | PLCopen TC6 与 IEC 61131-10 各导一次 | IEC 格式成功即根因确认；否则改写结论并排查菜单入口 |
| M10 | 仿真闭环上限 | `StartSimulator` → `OpenOnline` → 设备读写 | 明确"编译→仿真下载→RUN→读值"能否不依赖 GUI；否则 L3 降级 |

**判定规则**：M1+M2+M3+M5 通过 = 路线 A 最小闭环成立（模板工程 + XML 导入 + 编译 + 错误兜底）；
M3 失败才退路线 B；M7 成功率 <95% 时产品不承诺"全自动 UI"；M10 决定 L3 能否全自动。

### 9.4 三条落地策略（产品化建议）

| 策略 | 人工参与点 | 自动化率 | 适用前提 |
|---|---|---|---|
| **A 全自动（模板工程 + IEC XML + Rebuild + 证据导出）** | 0（仅最终审查） | ~90% | M1/M2/M3/M5 通过；错误明细可读（UI Output 兜底） |
| **B 半自动 babysit** | 人工只做"粘贴程序体 + 点转换" | ~80–90% | A 的 XML 导入失败时；其余环节仍全自动 |
| **C 手工** | 按操作清单导入 | ~30% | 兜底/离线/无自动化环境 |

**推荐**：**主线直接冲 A**——IEC 61131-10 格式有官方样例/XSD/手册三重证据，且"一次导入覆盖标签+程序体"，
比逐 POU 粘贴稳定得多；B 作为 A 的降级路径（同一 `GxWorks3Adapter` 接口下的另一种实现），C 永远保留。
错误明细是 A 的已知缺口：先用 UI 自动化读 Output 窗口兜底，再考虑补 dump 事件接口。

### 9.5 与现有 MCP 基础设施的关系

本会话已挂载两个 MCP server：

- `gxworks`（GXWorks Agent，GX Works2 / FX3U 路线，Ladder）——本项目**不复用其工程路径**，但可复用其上层的 Agent 协议/工程管理经验；
- `gxworks3`（GX Works3 GUI/COM 桥，含 `ui_action`）——**可直接复用**：其 COM 桥虽缺 interop DLL，
  但 32 位 PowerShell 晚绑定已被 Lead 实测可用（Product/Session 创建、`GetOpenIFVersion()`=34）；
  `ui_action` 可作通道 B 的 UI 底座。

建议：**项目内置一个 32 位 sidecar 适配器**（不依赖 MCP 进程存活），接口与 MCP 解耦；
若修复后的 `gxworks3` MCP 更稳，则在 sidecar 中调用它（可替换实现），避免重复造轮子。

## 10. 验证体系

### 10.1 五层金字塔

| 层 | 名称 | 验证内容 | 自动化 | 通过标准（建议） | 局限 |
|---|---|---|---|---|---|
| L0 | 本地分析 | 语法/类型/方言/规则 | 是 | E 级=0；W 级=0 或全部有解释 | 不等于能编译 |
| L0.5 | 宿主语义回归（可选） | 把 ST 编译到宿主引擎跑同一套用例做差分 | 是 | 用例全过；差异逐条解释 | 三菱 FB/扫描模型不保真，只当信号 |
| L1 | 原生编译 | GX Works3 真实编译 | 是 | error=0；warning 逐条解释；`IsProjectCompiled=TRUE` | 不证明行为 |
| L2 | 结构与安全规则 | 双线圈、互锁、急停门控、FB 实例、时基、除零、越界 | 是 | P0 规则 0 命中；P1 命中人工确认 | 规则覆盖有限 |
| L3 | 仿真场景 | 时序/边界/故障注入 | 是 | 用例全过；safety 类 100% | 仿真≠实机 |
| L4 | 实机/HIL | 真实 I/O、通信、扫描时间 | 半自动 | 验收用例全过 + 观测记录 | 成本高 |

> 每一层都必须产出可归档证据（报告/日志/快照/哈希），否则这层等于没做。
> 详细的规则库（20 条 P0/P1）、DSL 与执行语义见 `03-验证体系与行业实践.md` §2–§3。

### 10.5 安全与责任边界（红/黄/绿分级 + 人工 gate）

**程序分级**（写进工具，AI 无权自行降级）：

| 级别 | 定义 | 示例 | 允许 AI 生成？ | 验证要求 |
|---|---|---|---|---|
| 🔴 红 | 安全功能 / 与安全链直接相关 | 急停、安全门/光幕、安全 PLC 程序、危险能量直接控制 | **禁止** | 认证安全 FB/安全 PLC 方案，独立 V&V |
| 🟡 黄 | 与危险能量/运动/联锁相关 | 电机/伺服/变频输出、加热、报警互锁、手自动切换 | 可生成，**必须人工双签** | L0–L3 全过 + L4（仿真台/HIL）+ 双人复核 |

**工具行为边界**：

- ✅ 允许：生成代码/标签/测试用例；编译工程副本；启动/停止 GX Simulator3；仿真设备读写（白名单内）；只读诊断。

**人工 gate（建议 6 道）**：G0 需求冻结 → G1 生成准入（分级/白名单）→ G2 编译闸 → G3 仿真闸 →
G4 复核闸（黄级双签）→ G5 下载授权 → G6 现场验收。详细表格见 `03-验证体系与行业实践.md` §5.4。

## 14. 工程化与项目结构（建议）

```
src/
  spec/            # spec schema、解析、确认、diff
  ir/              # Program IR 类型与构建
  knowledge/       # CPU 档案/指令/FB/规则/模板（数据）+ 加载器
  gen/             # 模板组装、LLM 编排、修复循环、prompt
  analyze/         # 解析器/类型/控制流/安全规则（由 dialect 演进）
  native/          # GxWorks3Adapter（sidecar 客户端 / UI automation / 人工）
  sim/             # GX Simulator3 会话、测试 DSL 执行器
  emit/            # ST / 标签 CSV / 工程包
  deliver/         # 报告、追溯矩阵、manifest
  cli/             # 子命令
  mcp/             # MCP server
knowledge/         # 数据文件（JSON/MD），与 src 分离，便于评审
templates/         # GX Works3 工程模板（FX5U/iQ-R）
benchmark/         # 18 场景（spec + tests + 期望）
test/
docs/
```

技术栈建议：
- 核心：TypeScript/Node（沿用 v0.1，零运行时依赖的哲学保持）；
- 原生适配：C# 或 PowerShell 32 位 sidecar（GXW3Call 是 32 位 COM）；通过 stdio/JSON-RPC 与 Node 通信；
- 测试：`node:test`（已有）+ 基准 runner；CI 分两层（无 GX Works3 的单元/知识库层，和有 GX Works3 的 native E2E）。
- 版本管理：当前目录不是 git 仓库 → **M0 第一步先 `git init`**，建立基线，所有生成物可回退。

## 16. 需要你拍板的决策点

1. **CPU 优先级**：先只做 FX5U（iQ-F），还是 FX5U + iQ-R 双支持？（建议先 FX5U，iQ-R 作为 M4）
2. **产品形态**：个人提效工具 / 团队内部平台 / 对外产品？决定是否做 Web 审查 UI、多用户、许可与版本策略。
3. **落地通道**：是否接受 OpenIF COM + 必要时的 UI 自动化（会短暂占用 GX Works3 界面）？
   若坚持"零 UI 操作"，则错误明细/仿真导航环节可能退化，需明确可接受的自动化率。
4. **模型与数据**：云 API 是否可接受？工艺/程序数据是否敏感（决定是否需要本地模型）？
5. **与现有 MCP 资产的关系**：是否把本项目作为 `gxworks3` MCP 的上层 ST 工作流（共用适配器），还是完全独立实现？
6. **验证深度**：验收是否止于 GX Simulator3，还是必须实机 HIL（决定 M2 范围与硬件投入）？
7. **v0.1 处置**：渐进演进（推荐）还是推倒重写？
8. **是否立即启动 M0 的 10 个验证实验**（会创建临时 `.gx3` 工程、可能短暂占用 GX Works3）？

> 建议：先按默认假设推进 M0（FX5U、模板工程 + IEC XML 主线、云 API、渐进演进），决策点 1/3/5/8 在 M0 验证报告出来后一起定。

### 16.1 决策记录（2026-11-10，已确认）

| # | 决策点 | 结论 | 影响 |
|---|---|---|---|
| 1 | CPU 优先级 | **先只做 FX5U（iQ-F）**；iQ-R / 多机型推迟到 M4 | profile/知识库只做 FX5U（含 FX5UJ 差异）；目标值随之收敛 |
| 2 | 功能范围 | **核心优先**：先做"生成 → 本地检查 → IEC XML → 原生编译 → 报告"闭环；仿真/MCP/Web/RAG/基准后置 | M0/M1 只交付核心路径；M2 仿真按进度再定 |
| 3 | M0 实验 | **按需**：只在阻塞核心路径时做；优先 M3（XML 导入）、M5（编译）、M2（建工程）；M0/M9 因官方格式已核实可跳过 | 节省时间，先写代码后用真实工程验证 |
