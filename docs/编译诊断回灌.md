# 编译诊断回灌（M1 收尾）

## 为什么是"半自动"

GX Works3 没有公开的编译错误读取接口（OpenIF 只覆盖工程操作），
「全部转换」的 Error 列表只出现在 Output 窗口。因此工具链采用**半自动闭环**：

```
gen → 复制纯 ST 模板 → GX Works3 导入 XML → 全部转换
    → 从 Output 整理错误（JSON 或直接复制文本）
    → gen --llm --compiler-errors errors.json
    → 重新生成 → 再次导入验证
```

其中「读取 + 结构化 + 回灌」由 `src/gen/compiler-feedback.ts` 完成，
「带着错误重新生成」由 `src/gen/llm.ts` 的修复循环完成（需要 LLM 环境变量）。

## 错误文件格式

优先用 JSON（结构明确）；也接受从 Output 直接复制的纯文本。

```json
[
  { "code": "0x11021040", "message": "标签分配在锁存区，但未声明 RETAIN", "line": 12, "pou": "Main" },
  { "message": "未定义的标识符 'bFault'", "line": 30, "pou": "Main" }
]
```

纯文本示例（按行解析，能识别 `0x11021040`、`第 12 行`、`[Main]` 等）：

```text
1  Error  Main  Compile  标签未定义  0x11021040 第 12 行
2  Error  Main  Compile  非法设备地址 X198  第 20 行
```

> 样例文件：`bench/compiler-errors.sample.json`

## 用法

```bash
# 配置 LLM（缺少 AUTH_TOKEN 时工具会明确报 LLM_E_CALL，不会静默失败）
#   ANTHROPIC_BASE_URL / ANTHROPIC_AUTH_TOKEN（或 ANTHROPIC_API_KEY）

# 带编译错误重新生成（模板实例化失败时也会触发 LLM 兜底）
node --experimental-strip-types --no-warnings src/cli.ts gen specs/tank_level.json \
  --llm --compiler-errors bench/compiler-errors.sample.json -o out/fix1
```

产物 `manifest.json` 会记录：

- `generator`: `template` / `llm`
- `compilerDiagnostics`: 本次回灌的 GX Works3 错误（统一为 `GXW3_<code>`）
- `attempts`: 生成/修复轮数

## 当前边界

- 回灌后仍要求**本地解析 + 方言检查**通过；GX 编译错误本身不会在本地复现，
  因此"修复后是否真的能编译"仍需再次导入 GX Works3 验证（这正是半自动的含义）。
- 错误列表需要人工从 Output 整理；后续若 OpenIF 或 UI 自动化能稳定导出错误列表，
  可替换这一步而不改回灌逻辑。
- LLM 兜底默认走 `src/ai/client.ts`，测试用注入的假生成器，不触网。
