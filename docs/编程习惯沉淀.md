# 编程习惯沉淀机制（Style Profiles）

> 背景：PLC 编程没有唯一写法。不同工程师/公司对**命名、标签语言、模式划分、报警策略、停止语义、HMI 地址**的偏好不同。
> 以后用户会像本项目用户一样，通过对话描述需求、指出“应该这样/不要那样”。
> 本机制把这类偏好**持续沉淀为可版本化的档案**，避免每次从头猜。

## 1. 三个来源

| 来源 | 采集方式 | 示例 |
|---|---|---|
| 对话中的明确偏好 | AI 按 `profiles/questions.md` 提问；用户说“我们习惯…/以后都…/不要…” | “急停是暂停，不是断电” |
| 用户对生成物的修改 | 对比生成 ST 与用户改后版本（改名、结构调整、注释增删） | 把 `Y0` 改成 `bDown`、增加停止序列 |
| 评审/事故复盘 | 报警、卡缸、撞击等案例总结出的规则 | 卡缸后冻结步号、不强制全部 OFF |

## 2. 落地形式

```text
profiles/
├── questions.md                       # AI 首次接触用户时的习惯提问清单
├── industrial/robot_transfer_habits.json   # 首个真实档案（本用户）
└── <company|project>/<name>.json      # 后续：公司规范 / 项目覆盖
```

档案字段（v0）：

| 字段 | 内容 |
|---|---|
| `labels.language` | 标签语言（en/zh） |
| `naming` | 类型前缀、命名示例、备注 |
| `defaults` | 默认参数（如气缸超时 5s） |
| `codeStructure` | 模式划分、步进风格、FB 拆分、报警/停止/手动/注释习惯 |
| `hmi` | 触摸屏地址规划 |
| `alarmCodes` | 报警码分配规律 |
| `reviewChecklist` | 生成后自检清单（AI 逐条核对） |
| `notes` | 用户原话/背景，便于追溯 |

## 3. 应用到生成

```bash
# 单档案
node --experimental-strip-types --no-warnings src/cli.ts gen specs/xxx.json -o out \
  --style profiles/industrial/robot_transfer_habits.json

# 多级档案（个人 → 公司 → 项目，后者覆盖前者）
node --experimental-strip-types --no-warnings src/cli.ts gen specs/xxx.json -o out \
  --style profiles/user.json,profiles/company.json,profiles/project.json

# 先把多级档案合并成一个文件
node --experimental-strip-types --no-warnings src/cli.ts style merge profiles/user.json profiles/company.json \
  -o profiles/merged.json
```

当前自动应用（v0）：
- `labels.language`：spec 未设置时决定全局/局部标签中英文；
- `defaults.cylinderTimeoutMs`：spec 未设置时填入气缸超时；
- 生成结果 warnings 中记录“已应用编程习惯档案 + 应用项”。

其余字段目前是**结构化档案**：AI 读取后按档案生成/审阅，后续逐步变成生成器规则。

## 4. 优先级与版本管理

**本次对话/CLI 显式要求 > spec 显式字段 > style 档案 > 内置默认**

- 档案只填充“未显式设置”的项，不覆盖项目明确选择；
- 档案是普通 JSON，可 git diff/回滚；
- 建议命名：`<scope>/<industry>_<equipment>_habits.json`（如 `industrial/robot_transfer_habits.json`）。

## 5. 从「用户修改」提取候选规则

用户经常在 GX 里改完程序才体现真实习惯。对比「AI 生成 ST」与「用户修改后 ST」：

```bash
node --experimental-strip-types --no-warnings src/cli.ts style candidates \
  --generated out/robot_transfer_steps_v2.st --actual user_modified.st -o out/style_candidates
```

输出 `style_candidates.md` / `.json`，v0 可提取：

| 类型 | 依据 | 置信度 |
|---|---|---|
| `label-rename` | 全局标签按软元件地址配对后名称变化 | high |
| `local-rename` / `param-rename` | 同一 POU 同段同序号的变量/形参改名 | medium |
| `language` | 用户版本中文标识符占比高 | high |
| `naming-prefix` | 用户版 `b启动`/`n步号` 等前缀统计 | medium |
| `body-edit` | 正文行级增删改统计（仅提示，需人工看） | low |

候选规则只是建议，**人工确认后**写入 `profiles/`，跑测试并提交。

## 6. 对话中如何沉淀（AI 操作约定）

1. 用户首次提出新的编程偏好时，先确认（“以后这类项目都按…？”）；
2. 确认后写入对应档案字段，并在 `notes` 保留原话；
3. 若偏好影响生成器行为，先写档案 + 回归测试，再改生成器；
4. 每次用档案生成后，按 `reviewChecklist` 自检并在交付报告里说明；
5. 一次性需求写进 spec，不进档案。
