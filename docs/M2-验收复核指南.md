# M2 验收复核指南（给不熟悉 PLC 的你）

## 一句话

这条证据不代表"截图好看"，它验证的是：**AI 按模板生成的 ST 程序，在真实 PLC 仿真里行为正确**
（按下启动→输出 ON，松开保持，按下停止→输出 OFF）。

## 这和 ST 有什么关系？

有关系，而且是同一件事的三个阶段：

```
Spec（需求） → 模板生成 ST 源码（.st） → 转成 IEC XML → 导入 GX Works3（ST 程序）
                                                        ↓
                                              编译 Error 0（ST 语法/方言正确）
                                                        ↓
                                              仿真运行（GX 执行这段 ST）
                                                        ↓
                                              给 X 输入、看 Y 输出 → 截图/观测文件
```

- 截图里 `Y0` 变 1，是 GX Works3 **执行我们生成的 ST 代码**的结果；
- 想核对代码本身：打开 `sim/motor_start_stop.sim.json` 对应的 ST 源码
  （`node src/cli.ts gen bench/b_motor_start_stop.json -o out/b_motor` 生成 `b_motor.st`），
  能看到启动自锁/停止优先的逻辑；
- 如果 ST 写错了，要么 GX 编译直接报错（编译证据会失败），要么仿真行为与期望不一致
  （`sim` 断言会 FAIL 并指出哪个设备不一致）。

## 3 分钟复核步骤

1. 打开 `sim/motor_start_stop.sim.json`，看 4 个步骤的 `expect`；
2. 打开 `sim/motor_start_stop.obs.json`，对照 4 个步骤的 `values`（应当一一对应）；
3. 打开 `01-scenario-pass.png`，确认每张截图里 `Y0` 行 bit0 分别是 **1、1、0、0**；
4. 打开 `report.json`，确认 `ok: true`、`mismatchCount: 0`；
5. 想亲自跑一遍（可选）：
   ```bash
   node --experimental-strip-types --no-warnings src/cli.ts gen bench/b_motor_start_stop.json -o out/run
   copy templates\FX5U_ST_Template.gx3 %TEMP%\run.gx3
   # GX Works3：打开副本 → 工程 → 导入 → IEC61131-10 XML → 全部转换（应为 0 error）
   # 调试 → 仿真 → 开始仿真 → 在线 → 监视 → 设备/缓冲存储器批量监视
   # 按场景写 X0/X1，读 Y0，填入 obs.json，再执行：
   node --experimental-strip-types --no-warnings src/cli.ts sim sim/motor_start_stop.sim.json --observed sim/motor_start_stop.obs.json
   ```

## 判 PASS / FAIL 的规则

- **PASS**：所有带 `expect` 的步骤，实际观测值与期望一致；
- **FAIL**：`report.json` 的 `ok` 为 false，`steps[]` 里会给出
  `mismatches: [{ device, expected, observed }]`，直接指出哪个设备不符；
- 缺失步骤记为 `missing`，不算通过。

## 当前边界（如实说明）

- 这是**半自动**验证：GX Works3 没有公开的仿真读写 API，写输入/读输出需要人（或 Agent）
  在 GX 界面上操作，然后把观测值写成 JSON 交给工具断言；
- 截图是 GX Works3 的批监视窗口，不是工具自己画的；数值变化就是仿真执行 ST 的真实结果；
- 后续会做全自动驱动（OpenIF / UI 自动化），并扩展到更多场景（液位、报警、时序等）。
